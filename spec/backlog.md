# Product backlog

> The running list of desired features/changes, and the parking lot for items that belong to no
> feature yet. One line each. Lightweight — don't over-spec here; items earn detail as they move
> through the pipeline. (In `tracker`/`none` board mode this file is just the parking lot, with no
> sprints and no status ceremony: park an item, then promote it to a real feature/change in its time.)

Status values: idea · specified · planned · in-sprint · done · rejected

Type values: capability (new behavior) · change (to an existing feature) · debt (a conscious shortcut:
code that matches its spec but is badly made; cite the ENG-N rule it bends if `engineering.md` has
one). When several debt rows cluster around one surface, pay them down as a normal bounded feature
(e.g. `harden-error-handling`) whose acceptance criteria are exactly these rows, then mark them done.

`rejected` is the parking lot's memory: a human explicitly ruled the item out, and the What/why column
holds the durable reason (scope, philosophy, or a real constraint; "not now" is not a rejection, that
row stays `idea`). Before adding a new item, match it against rejected rows by concept, not wording
("night theme" matches a rejected dark-mode row); on a match, surface the prior ruling for the human
to confirm or consciously reopen instead of re-litigating it from scratch.
